# Deployment and recovery

## Local and VPS

Local development commands are in the root README. Docker Compose runs the API, a single worker, static frontend and Caddy TLS/authentication gateway. Copy `.env.example` to `.env`; never commit secrets. Set the real `DOMAIN`, a non-default `BASIC_AUTH_USER`, and a bcrypt `BASIC_AUTH_HASH` generated by `caddy hash-password`. The shared `bn_data` volume contains SQLite WAL files, original uploads and export files. After DNS points to the VPS and ports 80/443 are reachable, build, migrate, then start:

```sh
docker compose build
docker compose run --rm api alembic upgrade head
docker compose up -d
docker compose logs -f api worker caddy
```

The exact cause of the earlier failures is unknown; mirrored networking and WSL shutdown/restart were not tested, and no `.wslconfig`, source, proxy, or Docker daemon settings were changed.

Only Caddy publishes host ports 80/443. Its Basic Auth gate protects both the static frontend and API routes; API and web containers are reachable only on the internal Compose network. There is no unprotected Compose port for local browser access. Use the documented Vite and Uvicorn development commands for local work. A 2 GB VPS is only a starting estimate; observe memory during image processing and backups. Keep only one worker until lease/claim behavior is strengthened.

### Schema migrations

API and worker startup never create or alter tables. Run `docker compose run --rm api alembic upgrade head` after building the backend image and before starting either service. For local development, from `backend/`, run `uv run alembic upgrade head` before starting Uvicorn or the worker. A missing migration should fail visibly when a service accesses the schema; do not replace this step with `create_all`.

## Private server on the tailnet (`fx553vd-de`)

The production host is `serveradmin@fx553vd-de` (Ubuntu Server), reachable only on the Tailscale network. Tailscale Serve already publishes `https://fx553vd-de.tail3f59ee.ts.net/` (port 443) for another app, so BN-Inven gets its own HTTPS port. Tailscale terminates TLS with the tailnet certificate and forwards to Caddy on loopback. Caddy remains the only container with a host port.

Access control on this host is the tailnet itself: only devices signed in to the tailnet (and any device a node is shared with) can reach the app. Caddy uses `deploy/Caddyfile.tailnet`, which has no Basic Auth, so there is no second password prompt. Restrict access further with Tailscale ACLs if the tailnet ever includes other people. Never use the tailnet override on a host that is reachable from the internet; public deployments keep `infra/Caddyfile` with Basic Auth.

```text
tailnet client ──HTTPS :8443──▶ tailscale serve ──HTTP──▶ 127.0.0.1:8090 Caddy ──▶ api / web (internal)
```

### Development and production stay in separate folders

| | Production | Development |
| --- | --- | --- |
| Location | `/srv/apps/bn-inven`, a clean clone of `main` | The workstation clone (Windows/WSL). Optionally a separate server clone such as `~/dev/bn-inven`. |
| Who changes the code | Only `deploy/deploy.sh` (fast-forward to `origin/main`) | You, on branches, pushed to GitHub |
| Runtime | Docker Compose project `bn-inven` | `start-dev.sh` (Vite, Uvicorn `--reload`, worker), bound to `127.0.0.1` |
| Data | Docker volume `bn-inven_bn_data` (database, uploads, exports, pre-deploy backups) | `backend/data/` inside the dev clone |
| Secrets | `/srv/apps/bn-inven/.env`, mode 600 | The dev clone's own `.env`, normally `AI_PROVIDER=mock` |

Do not develop inside `/srv/apps/bn-inven`. The backend reads the repository-root `.env`, so a dev server started there would use the production AI key and settings. Dev dependency folders and a dev SQLite file would also sit next to production, and edited tracked files block fast-forward deploys. `deploy.sh` refuses to deploy while tracked files are modified. If you develop on the server, use a separate clone and open it through an SSH tunnel (`ssh -L 5173:127.0.0.1:5173 serveradmin@fx553vd-de`). Do not run `docker compose` in that clone unless you give it a different `COMPOSE_PROJECT_NAME`, or its volumes and containers will collide with production.

### One-time server setup

These steps need `sudo` on the server.

1. Install Docker Engine and the Compose plugin. Compose must be 2.24 or newer for the `!reset`/`!override` tags in `deploy/compose.tailnet.yml`. Then let `serveradmin` use Docker and log in again:

   ```sh
   sudo apt install docker.io docker-compose-v2
   docker compose version
   sudo usermod -aG docker serveradmin
   ```

2. Clone the repository and create the production `.env`:

   ```sh
   git clone https://github.com/vdtongdev/bn-inven.git /srv/apps/bn-inven
   cd /srv/apps/bn-inven
   cp .env.example .env && chmod 600 .env
   ```

   In `.env`, set `DOMAIN=:80` and `BASIC_AUTH_HASH=unused`. `docker-compose.yml` requires `DOMAIN` and `BASIC_AUTH_*` to have values, but the tailnet override does not pass them to Caddy. Set `CORS_ORIGINS=https://fx553vd-de.tail3f59ee.ts.net:8443` and uncomment `COMPOSE_PROJECT_NAME`, `COMPOSE_FILE` and `BN_HTTP_PORT`. Optionally add OpenRouter settings. `DATABASE_URL` and `STORAGE_PATH` are overridden by Compose.

3. Run the first deploy: `bash deploy/deploy.sh --force`. It builds the images, backs up any existing database, runs `alembic upgrade head`, starts the stack and waits for `/api/health`.

4. Publish the app on the tailnet without touching the existing port 443 mapping:

   ```sh
   sudo tailscale serve --bg --https=8443 http://127.0.0.1:8090
   tailscale serve status
   ```

   Open `https://fx553vd-de.tail3f59ee.ts.net:8443/`.

5. Turn on automatic synchronization with GitHub `main`:

   ```sh
   sudo cp deploy/systemd/bn-inven-deploy.service deploy/systemd/bn-inven-deploy.timer /etc/systemd/system/
   sudo systemctl daemon-reload
   sudo systemctl enable --now bn-inven-deploy.timer
   ```

### Synchronization with GitHub `main`

Every 5 minutes the timer runs `deploy/deploy.sh`, which takes these steps:

1. Fetches `origin/main` and compares it with the last successfully deployed commit, stored in `~/.local/state/bn-inven/deployed-commit`. It exits immediately when the two match.
2. Fast-forwards the checkout. It never merges, rebases or force-resets.
3. Builds the images, writes a SQLite snapshot to `/data/backups/pre-deploy-*.db` (keeps 10), and runs `alembic upgrade head` explicitly.
4. Restarts the stack and checks `/api/health`. A commit is recorded as deployed only after the check passes, so a failed build or migration is retried on the next run instead of being skipped.

Anything pushed to `main` reaches production within about 5 minutes, so merge to `main` only what is ready to run. To deploy without waiting, run `sudo systemctl start bn-inven-deploy.service` or `bash deploy/deploy.sh`. To pause automatic deploys, run `sudo systemctl stop bn-inven-deploy.timer`. Follow logs with `journalctl -u bn-inven-deploy.service` and `docker compose logs -f api worker caddy`. Pre-deploy snapshots live on the same disk and do not replace the off-site backups described below.

To roll back, revert the bad commit on GitHub `main` and let the timer deploy it. A rollback that crosses a migration also needs the matching pre-deploy snapshot restored, because Alembic downgrades are not part of the deploy.

## Access, origins and secrets

The public self-hosted deployment uses Caddy Basic Auth in front of both the static frontend and API. The private tailnet deployment relies on Tailscale for access control instead (see above). CORS is limited to configured origins and supports credentialed browser requests. Load any eventual AI provider key only on the backend. No shared application token is sent to or compiled into the browser.

### Optional OpenRouter vision extraction

Mock extraction remains enabled by default and requires no network key. To use OpenRouter, set `AI_PROVIDER=openrouter`, `AI_API_KEY` to a server-side key, and optionally `AI_MODEL` (the temporary, unvalidated test selection is `nvidia/nemotron-3.5-super-vl:free`) in the ignored root `.env`. Local backend settings load that root file; Compose passes its environment into API and worker containers. Never use a `VITE_*` variable for the key. `bn_inven` may be used as a dashboard label only; it is not sent as a request parameter.

The worker sends an EXIF-corrected, resized, re-encoded JPEG copy to the fixed OpenRouter chat-completions endpoint. It does not replace stored originals. Provider response JSON, model, prompt version and returned usage/cost metadata are stored with the extraction result for traceability. Permanent auth/request/schema failures are not retried; transient network, rate-limit and server errors use the job's bounded retries. Uncertain values remain null and all output remains a human-reviewed suggestion. The selected model's catalog accuracy and actual billed cost have not been validated. Keep `AI_PROVIDER=mock` for local tests and no-cost development.

## Cloudflare Pages

Build the `frontend/` directory with `npm ci`, build command `npm run build`, output directory `dist`. Caddy on the VPS does not protect a Cloudflare Pages origin. Configure Cloudflare Access (or an equivalent identity-aware gateway) for both the Pages site and the API hostname, or put the API behind an authenticated same-origin gateway. Set `VITE_API_BASE_URL` to that protected API endpoint and set backend `CORS_ORIGINS` to the exact Pages origin. Browser API requests include credentials; the gateway must support its cookie/session flow across the chosen origins. Do not put passwords, access tokens, or provider credentials in `VITE_*` variables. The self-hosted static option is the internal `web` service in Compose, reachable publicly only through Caddy.

The frontend's Node packages are build and test dependencies; production installs omitting dev dependencies contain no packages. The current full dependency audit reports four low findings in `vite-plugin-pwa`'s Workbox chain: `deepmerge@4.3.1` (`GHSA-gcqx-w48m-w2h4`) via `workbox-build` and `@rollup/plugin-node-resolve`. The npm audit fix suggestion downgrades `vite-plugin-pwa` to `0.2.1` as a breaking change, so that downgrade is not applied. The Caddy image copies only the generated `dist/` assets. Recheck the audit and upstream PWA/Workbox releases during dependency updates; this audit finding is not proof of exploitability in the static runtime.

## Backups

Stop API and worker briefly for a simple consistent SQLite snapshot, or use SQLite's backup API while online. Copy the database (including WAL-consistent state), `uploads/`, and `exports/` to off-site storage. Keep encrypted, versioned backups and test restores. A raw copy of only the main `.db` file while WAL is active can omit committed transactions.

Restore steps:

1. Install Docker on the replacement Linux VPS and copy the Compose/config files and protected `.env`.
2. Restore database and file directories into the `bn_data` volume with ownership allowing the containers to read/write.
3. Start one API and one worker; check `/api/health`, job queue state and a known photo/export.
4. Keep the prior host backup until restored catalog data and source images are confirmed.

Cloudflare R2 or another object store can be added behind a backup adapter later; it is not required for the initial deployment.

## Operations

`GET /api/health` reports process health. Logs go to container stdout with timestamps and severity. Monitor disk use, failed jobs, backup age and provider usage once a real provider is selected. HTTPS and authentication must be enabled before exposing the service publicly.
